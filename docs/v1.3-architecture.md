## 1. North Star and the acceptance test

### North Star

> PurrCode behavior becomes **configuration-driven** instead of **source-code-driven**. A user
> installs a skill, adds an MCP, defines a project agent, defines a custom command, defines a
> hook, and binds a different model / tools / permissions per task class — **without modifying
> Rust, forking PurrCode, or recompiling.**

### The acceptance test — Zero-source-change extension challenge

Using only `.purrcode/` config, settings, skills, MCP, agents, commands and hooks, a user must be
able to:

1. Create a read-only **Security Reviewer** agent.
2. Give it its own model.
3. Forbid it from writing files.
4. Install a security skill.
5. Connect an MCP server.
6. Create `/security-review`.
7. Have it auto-read the current diff.
8. Have the reviewer invoke the skill.
9. Have the reviewer invoke the MCP tool.
10. Have **PawGate** authorize the external tool.
11. Get **structured findings** back.
12. Have those findings land in the main agent's context.
13. Ask the main agent to fix two of them.
14. Have a **hook** auto-run validation after the fix.
15. Have every tool / action / evidence be traceable.

**Acceptance condition:** all fifteen work with **no new Rust code path named "security
reviewer"**. The only Rust that ships is generic machinery: a capability resolver, a tool
registry, a descriptor lattice, a hook dispatcher, a graph. If an implementer finds themselves
writing `if agent_name == "security-reviewer"`, the design has failed.

### Out of scope for v1.3 — do not design these

Plugin marketplace (local path + git install + signed package + publisher identity only);
visual workflow builder; agent swarms / consensus / debate; remote cloud execution; enterprise
RBAC / SSO / tenancy (leave interface seams only).

## 2. Current-state map

This section is what the implementers should trust instead of re-reading the whole workspace.

### 2.1 Tool / action invocation path

There is no generic "tool" abstraction. There are two disjoint action systems. The **model-facing**
type is `AgentAction` (`crates/agent-runtime/src/schema.rs:87`), a closed four-variant enum —
`Read`, `ReadCommand`, `WriteFile`, `DeleteFile` — emitted as structured output inside `AgentTurn`
via `schema_for!(AgentTurn)` (`crates/agent-runtime/src/agent.rs:2337`). `ModelRequest.tools` is
`Vec::new()` at every call site (`agent.rs:1359`, `:1461`, `:2325`), so the provider is never given
a tools array at all. The **canonical runtime** type is `ProposedAction`
(`crates/runtime-core/src/lib.rs:563`) with five variants: `Command`, `RepositoryRead`, `WriteFile`,
`DeleteFile`, `ExternalTool`. `normalize_action` (`crates/agent-runtime/src/normalize.rs:73`) is the
only bridge and can only produce the middle three — `ExternalTool` is structurally unreachable from
the model.

Authorization is a digest-bound, single-use capability. `Policy::evaluate`
(`crates/pawgate-runtime/src/lib.rs:81`) returns a `JudgmentDecision`
(`crates/runtime-core/src/lib.rs:604`); `apply_permission_mode` (`normalize.rs:377`) applies the
session's standing mode; the decision's `ActionConstraints` (`runtime-core/src/lib.rs:579`) are
hashed together with the action by `ProposedAction::digest` (`runtime-core/src/lib.rs:572`, blake3
over `serde_json::to_vec(&(self, constraints))`) and written by `SessionStore::authorize`
(`crates/ninelives-recovery/src/lib.rs:179`). Execution re-derives the digest and calls
`consume_authorization` (`ninelives-recovery/src/lib.rs:258`), which atomically flips `consumed_at`
— at-most-once. `ToolRuntime::execute` (`crates/claw-sandbox/src/lib.rs:84`) rejects `ExternalTool`
outright at `claw-sandbox/src/lib.rs:122`.

Bare `JudgmentDecision::Allow` is a hard error at execution time
(`AgentError::UnsafeUnconstrainedAllow`, `agent.rs:3238`) — every real allow must carry constraints.
`ApprovalAuthority::SignedPolicy { policy_id }` (`runtime-core/src/lib.rs:748`) is **defined but
never constructed anywhere in the workspace**; signed org packs restrict the `Policy` but the
resulting authorizations are still stamped `DeterministicPolicy`.

There is **no type named `ExecutionEvidence`**. The in-memory product is `ExecutionResult`
(`claw-sandbox/src/lib.rs:61`); its durable projection is the event quartet
`ExecutionStarted` / `ExecutionFinished` / `ActionOutputRecorded` / `ValidationRecorded`
(`runtime-core/src/lib.rs:1304`, `:1307`, `:1316`, `:1325`). The multi-read batch path
(`agent.rs:2544`–`:2637` → `ToolRuntime::execute_batch`, `claw-sandbox/src/lib.rs:133`) appends
**none** of `ExecutionStarted` / `ExecutionFinished` / `ValidationRecorded` / `EvidenceLinked` —
batch reads are materially less evidenced than scalar ones, and `SessionState.status` never enters
`Executing`. `EvidenceBundle` (`crates/evidence-bundle/src/lib.rs:11`) is the exportable audit
artifact, reachable only from the CLI (`crates/purrcode-cli/src/main.rs:2166`); **no daemon route
exports it**, and its redaction table (`evidence-bundle/src/lib.rs:123`) is keyed on the serde event
tag, so an `ExternalTool`'s `arguments` blob is exported verbatim.

### 2.2 MCP and skill invocation

`ProposedAction::ExternalTool` (`runtime-core/src/lib.rs:163`) is minted in exactly two ways:
`McpHost::translate` (`crates/mcp-host/src/lib.rs:347`), and four hand-built pseudo-server sites in
the daemon (`crates/purrcode-daemon/src/lib.rs:10197` skill-registry search, `:10543`
download-source-archive, `:10739` web-research fetch-page, `:11237` skill-store install). The only
HTTP entry point is `POST /v1/sessions/{id}/mcp` (route registered at
`purrcode-daemon/src/lib.rs:504`) → `invoke_mcp` (`:3771`), 285 lines that reimplement the native
authorization pipeline by hand.

`McpServerConfig` (`crates/mcp-host/src/lib.rs:293`) is the entire authorization surface for MCP,
and its scope is **per server, not per tool**: one `network` bool, one `working_directory`. Only
`trusted_tools` / `deny_tools` are per-tool, as bare name lists, consulted at exactly one call site
(`purrcode-daemon/src/lib.rs:3847`, `:3853`). `McpToolDescriptor` (`mcp-host/src/lib.rs:330`) has
four fields — `server_id`, `name`, `description`, `input_schema` — and `discover_tools`
(`mcp-host/src/lib.rs:385`) silently drops MCP's `annotations` object (`readOnlyHint`,
`destructiveHint`, `idempotentHint`, `openWorldHint`), `outputSchema`, and `title`. `input_schema`
is discovered, serialized to the client, and **never validated against**.

PawGate's `ExternalTool` arm (`pawgate-runtime/src/lib.rs:173`–`:211`) validates only working-directory
equality and identifier safety, then unconditionally returns `RequireApproval` with `network: false`
hardcoded at `:204`. Because `authorize_external` (`mcp-host/src/lib.rs:453`) requires
`constraints.network == server.network` (`:469`), **any MCP server configured with `network = true`
is unreachable through every authorized path** — that case has never executed.

Skills are not tools. `SkillResolver::resolve` (`agent-runtime/src/agent.rs:4255`) returns
`CapabilityResolution::InstalledSkill { skill_id, tool_name }` (`agent.rs:4245`); `tool_name` is set
to a copy of `skill_id` (`purrcode-daemon/src/lib.rs:7800`) and **has no reader anywhere**. The
caller (`purrcode-daemon/src/lib.rs:4986`–`:5014`) emits telemetry events and discards the
resolution — the agent turn is byte-identical whether or not a skill matched.

### 2.3 Slash-command registry

`builtin_commands()` (`crates/purrcode-daemon/src/commands.rs:45`) returns a hardcoded
`Vec<CommandDescriptor>` of 18 entries. `CommandDescriptor` (`commands.rs:37`) is
`#[derive(Clone, Copy, Debug, Serialize)]` with four fields, **all `&'static str`**, plus
`execution: CommandExecution` (`commands.rs:20`), a closed three-variant enum tagged `kind`:
`Daemon { method, path }`, `Client`, `Prompt { prompt }`. It is `pub(crate)`; the JSON at
`GET /v1/commands` (route at `purrcode-daemon/src/lib.rs:576`, handler `list_commands` at `:9387`)
is the only public surface. `list_commands` takes no repository parameter — it **structurally cannot
serve per-project commands** today.

`command_for` (`commands.rs:200`) matches only the leading lowercased first word, first-match-wins,
and is called on the per-message hot path from `append_message`
(`purrcode-daemon/src/lib.rs:2409`), which refuses all three kinds with `BadRequest`. The exhaustive
match at `:2410`–`:2428` is what makes the enum's closedness load-bearing. `start_session`
(`:2217`) **never calls `command_for`** — `/undo` posted as an objective still becomes a literal
session objective.

The IDE mirrors the enum with owned `String`s plus an `Unknown` variant
(`crates/purrcode-ide/src/model.rs:1650`), fetches once at startup
(`crates/purrcode-ide/src/app/mod.rs:836`), and dispatches `Daemon` by POSTing the published path
verbatim with the daemon bearer token (`app/mod.rs:1111`–`:1115` → `daemon.rs:1492` →
`daemon.rs:2329`, `format!("{}{path}", base_url)`). The `Client` arm is a hardcoded match over nine
name literals (`app/mod.rs:1117`–`:1138`). The TUI keeps a **second, entirely independent static
registry** (`crates/purrcode-tui/src/command_palette.rs:23`,
`crates/purrcode-tui/src/ui_actions.rs:390`) and never calls `GET /v1/commands`.

### 2.4 Skills subsystem

Three crates. `crates/mcp-host/src/lib.rs` owns the on-disk format: a skill directory must contain
**exactly** `SKILL.md` + `manifest.toml` (`discover_skills:75`, `load_skill:177`, both hard-fail if
either is missing). `SkillManifest` (`mcp-host/src/lib.rs:22`) is TOML; `required_tools`,
`required_permissions`, `secrets_required` and `model_capabilities` are parsed and **never
referenced anywhere in the workspace**. There is no `capabilities` field, no description, no tool or
output-schema declaration. `LoadedSkill.instructions` (`mcp-host/src/lib.rs:61`) — the `SKILL.md`
path — has **zero readers**; the prompt bundle is never loaded into any context.

`crates/skill-store/src/lib.rs` owns the installed library: its **own** SQLite file
(`SkillStore::open`, `skill-store/src/lib.rs:122`) with a hand-rolled `migrate` (`:133`) that probes
`PRAGMA table_info` and `ALTER TABLE` — **not** the `migrations/` directory — plus a copied file tree
under `<library_root>/{user,repository,session}/<skill_id>/` (`scope_root:662`).
`find_by_capability` (`:488`) is a lowercase substring match over `skill_id`, `source_type` and
`publisher` only — it reads no manifest and no declared capability list. That is the entire
capability model today. `approved_permissions` is opaque JSON, stored, rendered by the TUI
(`crates/purrcode-tui/src/skill_browser.rs:125`), and **enforced by nothing**.

Two divergent digest implementations must agree and do not: `skill_content_digest`
(`skill-store/src/lib.rs:732`) rejects symlinks, non-UTF-8 paths and escapes and enforces
10 000 files / 100 MiB; `skill_digest` (`mcp-host/src/lib.rs:232`) does none of that and recurses on
`path.is_dir()`, following symlinked directories. The daemon's whole install chain digests with the
**mcp-host** one (`purrcode-daemon/src/lib.rs:11084`, `:11319`, `:11415`, `:11462`).

Critically: **a prompt-only skill cannot be installed today.** `Qualifier::qualify`
(`mcp-host/src/lib.rs:1023`–`:1050`) sets `entrypoint_ok = !manifest.entrypoints.is_empty() && …`,
so an empty entrypoint map fails the `entrypoints` case → `blocked = true` →
`QualificationStatus::Blocked` (`:1126`), and `propose_skill_install`
(`purrcode-daemon/src/lib.rs:11156`–`:11171`) rejects any skill without a dynamic qualification
fixture. `enabled` has exactly one enforcement site (`skill-store/src/lib.rs:530`) and it only
affects telemetry.

### 2.5 Agent configuration and the policy ceiling

**There is no agent entity.** An agent is a session. Everything an agent "is" comes from three
session-level values assembled fresh in `run_agent_operation`
(`crates/purrcode-daemon/src/lib.rs:4796`): models via `resolve_role_models` (`:4754`, which
force-inserts the session model as `coding_worker` at `:4765`), a compile-time system prompt
(`developer_instructions`, `crates/agent-runtime/src/context.rs:788`), and `SessionControls`
(`crates/runtime-core/src/adaptation.rs:1028`). `NativeAgent` (`agent-runtime/src/agent.rs:206`) has
eleven fields and **no name and no identity**. `model_for(role)` (`agent.rs:255`) is a `BTreeMap`
lookup on a loose `&str` that falls back to `coding_worker` and `.expect()`-panics if absent.

`crates/model-selection` is dead code for the daemon: `ModelRole` (`model-selection/src/lib.rs:34`),
`select_models` (`:357`) and `MANDATORY_ROLES` (`:305`) have no callers outside their own crate.
Worse, the two role vocabularies disagree: `AppConfig::canonical_model_role`
(`crates/provider-gateway/src/lib.rs:982`) accepts `reviewer`/`utility`/`router` and **rejects**
`scout`/`fast_router`, which is exactly what `agent.rs:1429` looks up.

The ceiling is `effective_policy` (`purrcode-daemon/src/lib.rs:5326`) — and **it only exists when a
signed org pack is configured.** With one, `Policy::load_effective`
(`crates/pawgate-runtime/src/lib.rs:68`) calls `SignedPolicyPack::restrict` (`:326`), which is a real
lattice (see §9). Without one, the else-branches at `purrcode-daemon/src/lib.rs:5338`–`:5340` load
`<repository>/policies/default.toml` (`resolve_policy_path`, `pawgate-runtime/src/lib.rs:701`) or
fall back to `Policy::default()`. **In the default single-user install the project repository already
defines its own policy with nothing above it.** `restrict` is private (`fn restrict`, no `pub`).

`apply_permission_mode` (`agent-runtime/src/normalize.rs:377`) is the last word before authorization
and it runs *after* both `Policy::evaluate` and the contextual judge: `Auto` turns `RequireApproval`
into an allow (`:385`), and `FullAccess` turns even `Deny` into `AllowWithConstraints(read_only(..))`
(`:388`–`:393`). `SessionCreated.authority_mode` is written (`purrcode-daemon/src/lib.rs:2285`) and
**never read back for enforcement**.

Supervisor workers are not sandboxed agents: `WorkerSpec`
(`crates/supervisor-runtime/src/lib.rs:52`) is `{ id, objective, dependencies, model: Option<String> }`,
`JudgedSupervisorWorker::execute` (`purrcode-daemon/src/lib.rs:1150`) sends a hardcoded developer
prompt (`:1212`), takes exactly one action, and the supervisor asserts
`output.model_requests <= 1` (`supervisor-runtime/src/lib.rs:355`). One `Policy` is built at
`purrcode-daemon/src/lib.rs:1412` and cloned into every worker (`:1438`).

`ScoutRequest.allowed_action_kinds` (`agent.rs:124`) is populated at `agent.rs:2156` and **never
read** — `run_scout` enforces read-only structurally at `agent.rs:1549` instead. This is the exact
declared-but-unenforced pattern v1.3 must not repeat.

### 2.6 Configuration loading and precedence

Two live config formats, both TOML, and **no project-level declarative config at all**.
`AppConfig` (`crates/provider-gateway/src/lib.rs:604`) is loaded whole by `AppConfig::load`
(`:743`) from `ProjectDirs::from("dev","PurrCode","PurrCode").config_dir().join("config.toml")`
(`crates/purrcode-cli/src/main.rs:3526`) — no env override, no merging. Its
`#[serde(flatten)] extensions: BTreeMap<String, toml::Value>` (`:617`) is the existing
forward-compat seam; `[mcp.servers.*]` and `[codex]` already ride it and are re-parsed on demand
(`mcp_section`, `purrcode-daemon/src/lib.rs:3756`). The daemon re-reads the file from disk at
roughly 30 call sites with **no caching**. `purrcode.toml.example` at the repo root is loaded by
nothing.

The precedence chain is implemented **twice** with no shared helper —
`effective_policy` (`purrcode-daemon/src/lib.rs:5326`) and `load_policy`
(`crates/purrcode-cli/src/main.rs:3499`).

`.purrcode/` exists but holds **only runtime scratch**: `<repo>/.purrcode/worktrees/<session-uuid>`
(`crates/repository-engine/src/lib.rs:196`–`:206`), `<worktree>/.purrcode/context.db`
(`purrcode-daemon/src/lib.rs:5063`), a CLI-only `<repo>/.purrcode/skills` the daemon ignores.
`ensure_purrcode_excluded` (`repository-engine/src/lib.rs:928`–`:949`) writes a blanket `.purrcode/`
line into `.git/info/exclude`, so **committed config under `.purrcode/` would be invisible to git**
for anyone whose checkout PurrCode has touched. PawGate additionally hard-requires that any file
mutation target a path containing both a `.purrcode` and a `worktrees` component
(`pawgate-runtime/src/lib.rs:226`–`:237`). The one existing project-*config* convention is
`<repo>/policies/default.toml`, which is **not** under `.purrcode/`; the one existing
project-*instruction* convention is the root files in `INSTRUCTION_FILES`
(`crates/purrcode-daemon/src/project_context.rs:61`).

Migrations live at `migrations/000N_<name>.sql`, `include_str!`'d as consts at
`crates/ninelives-recovery/src/lib.rs:12`–`:14` and executed in order by `migrate`
(`:122`–`:131`) inside one IMMEDIATE transaction. **There is no version gating** — every file
re-runs on every open, so every statement must be idempotent and each file ends with
`INSERT OR IGNORE INTO schema_migrations(version, applied_at) VALUES (N, datetime('now'));`.
Existing: `0001_initial.sql`, `0002_automations.sql`, `0003_session_workspace.sql`.
**Next free number: 0004.**

`serde_yaml = "0.9"` is declared at `Cargo.toml:81` but wired into exactly one crate,
`crates/provider-import` (`provider-import/Cargo.toml:12`). It is unmaintained upstream.

### 2.7 Context, retrieval and project intelligence

Retrieval is **lexical FTS5 + a SQL symbol-name LIKE scan + three re-rank boosts. There are no
embeddings anywhere in the retrieval path.** Everything lives in one SQLite file per session
worktree at `<worktree>/.purrcode/context.db` (`purrcode-daemon/src/lib.rs:5063`). The schema is a
single `const SCHEMA` string (`crates/whisker-context-engine/src/lib.rs:2302`–`:2356`) applied
unconditionally by `execute_batch(SCHEMA)` in `ContextIndex::open` (`:433`) — whisker has **no
migration or versioning mechanism at all**, and `clear_index` (`:1268`) wipes all eight tables on
every Tier-0 rebuild (`:537`). A project graph stored there dies with the session.

`ContextIndex::retrieve` (`whisker-context-engine/src/lib.rs:948`) is the single ranking function:
phase 1 bm25 over `chunks` with additive bonuses (path substring +5000 at `:975`, git-changed +2500
at `:976`, commit recency at `:977`); phase 2 `LIKE '%term%'` on `symbols.name`/`kind` (`:1020`) with
a flat +3000 (`:1050`); phase 3 import proximity +1500 (`:1128`), cochange +1000 (`:1200`),
test relation +2000 (`:1206`) — **boosts only, never expansion**, explicitly commented at
`:1194`–`:1196`; phase 4 sorts by `score_millis` (`:1212`) and truncates to `RetrievalBudget`
(12 hits / 64 KiB, `:409`).

Already-derivable graph facts: `symbols(path,name,kind,line)` from tree-sitter (`:1382`);
`cochanges(path_a,path_b,occurrences)` from `git log -100 --name-only` (`:1791`–`:1830`), real
weights; `test_relations(test_path,source_path,confidence)` (`:1373`) — but pure filename
substitution (`is_test_path:1722`, `probable_source_path:1735`) with a hardcoded 0.5 confidence that
is never read. `imports(source_path, target)` is **not** a file→file edge: `extract_imports`
(`:1749`) is line-prefix string scraping (not tree-sitter) and stores the raw unresolved text.

`HitReason` (`whisker-context-engine/src/lib.rs:375`) already enumerates
`MatchedQuery`/`ImportProximity`/`Cochange`/`TestRelation`/`Unspecified` — the provenance vocabulary
exists — but the payloads are set to `hit.path` itself (`:1130`, `:1202`, `:1208`), so **the edge's
counterparty is discarded**, and the assignments overwrite rather than accumulate.
`ContextIndex::symbols` (`:1238`) is dead in production: its only caller is a unit test at `:2508`,
despite a daemon doc comment at `purrcode-daemon/src/lib.rs:9337`–`:9338` claiming `#symbol`
references use it — `attach_reference` actually shells out to `git grep`
(`crates/purrcode-daemon/src/project_context.rs:341`–`:361`).

LSP is v1.2's real symbol intelligence (`crates/lsp-client/src/lib.rs:775`, `workspace_symbols:873`,
`references:838`, `definition:828`) and **persists nothing**. `LspManager::key` (`:788`) keys servers
by **file extension only**, so a second worktree with `.rs` files silently reuses the server rooted
at the first root. `FailureClass` (`crates/validation-runtime/src/lib.rs:93`) is a typed vocabulary
and `classify_failure` (`:150`) runs per turn, but the result is only formatted into a prompt string
(`agent-runtime/src/context.rs:752`) — failures are recoverable by replay, not queryable.

`build_messages` (`agent-runtime/src/context.rs:611`) maintains an invariant asserted by the test at
`context.rs:1235`: per-section `ContextLedgerSection` token sums must telescope to the aggregate
estimate. `WhyIncluded` (`runtime-core/src/lib.rs:798`) has only
`AlwaysPresent`/`MatchedQuery`/`RecentEdit`/`Pinned` — **a graph-derived hit has no honest label
today.**

### 3.2 Seam by seam

**Seam 1 — User Intent → Capability Resolver.** Today intent arrives as an `AgentOperation`
(`purrcode-daemon/src/lib.rs:4373`) or a refused slash command (`commands.rs:200`). v1.3 adds a
resolution step *before* the operation is spawned. `CapabilityRegistry::resolve(CapabilityId)`
returns a ranked `Vec<CapabilityProvider>`; the daemon picks the highest-precedence provider and
turns it into an `AgentOperation::Capability`. Nothing in the agent loop learns the word "security".
Precedence is the same three-layer rule everywhere: **Project > User > Built-in**, ties broken by
explicit `priority`, then by provider id, so resolution is deterministic and testable.

**Seam 2 — Capability Resolver → Agent Profile / Skill / Command.** These three are *providers of the
same capability*, not competing subsystems. An `AgentProfile` says who runs it and under what
ceiling; a `SkillDescriptor` says how the work is done (instructions + required context + allowed
tools + output schema + optional scripts); a `CommandDescriptor` says how it is triggered and what
context is auto-attached. `/security-review` is a Command bound to an Agent that is allowed a Skill.

**Seam 3 — Providers → ToolRegistry.** The registry is populated per-turn from four sources: the
built-in native table (a `const` in runtime-core: the 10 `RepositoryReadAction` kinds + write +
delete), MCP discovery (`McpHost::discover_tools`, `mcp-host/src/lib.rs:385`), installed skills
(`SkillStore`), and project config. All four go through `CapabilityRegistry::admit`, which is the
only mint. **This is the seam that makes an MCP or skill tool proposable by the model at all**,
because `schema_for!(AgentTurn)` (`agent.rs:2337`) becomes a registry-driven schema build instead of
a fixed derive.

**Seam 4 — ToolRegistry → PawGate.** `Policy::evaluate` gains the descriptor:
`evaluate_tool(&self, action, descriptor, repository)`. The provider-aware `ExternalTool` arm
(`pawgate-runtime/src/lib.rs:173`–`:211`) collapses into one generic arm reading four descriptor
fields. `evaluate_file_mutation` (`:215`) becomes the enforcement of
`FilesystemScope::Worktree` rather than a per-variant special case. The
`read_only_programs` / `approval_required_programs` allowlists (`pawgate-runtime/src/lib.rs:15`–`:17`)
become the descriptor registry for the native `Command` provider rather than a `Policy` field —
though `Policy` keeps them, because they are also the **ceiling** those descriptors are restricted
against (§9). **Argument schema validation runs here, before `store.authorize`, never in the
provider adapter** — otherwise a malformed call is authorized and then fails past the point of audit.

**Seam 5 — PawGate → Execution.** Unchanged in shape, extended in two ways. `ProposedAction::digest`
gains the descriptor digest as a third hashed element, so a registry refresh invalidates outstanding
capabilities. `ToolRuntime::execute` (`claw-sandbox/src/lib.rs:84`) replaces the
`ExternalTool => Err(UnsupportedConstraint)` arm at `:122` with a match on `descriptor.provider`.
The trust bypass at `purrcode-daemon/src/lib.rs:3863`–`:3876` is **deleted**: `trusted` becomes
`ApprovalPolicy::PreAuthorized` evaluated *inside* `Policy::evaluate_tool`, restoring PawGate as the
single decision point.

**Seam 6 — Execution → ExecutionEvidence.** A new `ExecutionEvidence` type replaces the ad-hoc
quartet-plus-`ExecutionResult` shape as the thing handlers construct. It carries the four
traceability answers the product owner named: *can it be called* (descriptor + registry admission),
*why it was allowed* (`JudgmentDecision` + `ApprovalAuthority`), *what exact scope was authorized*
(`ActionConstraints` + `descriptor_digest`), *what happened and what evidence came back*
(`ExecutionOutcome` + `structured_output`). The batch read path
(`agent.rs:2544`–`:2637`) must be brought up to the same evidencing before any network-reaching
descriptor is allowed onto it.

**Seam 7 — Evidence → Context / Memory / Graph.** Structured tool output becomes a
`PinnedSection` with a new `PinnedOrigin::ToolFindings` (this is acceptance-test step 12: findings
land in main-agent context as *attached data*, not as re-parsed prose), and simultaneously a
projection into the project graph (`failure`, `decision`, `task` nodes). The graph feeds back into
retrieval at `AgentContextIndex::retrieve` (`agent-runtime/src/context.rs:98`) — a one-line
pass-through today, and the cheapest interception point covering 100 % of production retrieval,
because `agent-runtime` is the only crate depending on `purrcode-whisker`
(`crates/agent-runtime/Cargo.toml:12`).

**Naming convention, verified against `Cargo.toml`:** the workspace member path is
`crates/<dir>` and the package name is **always** `purrcode-<something>`. The `<something>` is
usually the directory name verbatim (`crates/agent-runtime` → `purrcode-agent-runtime`,
`crates/skill-store` → `purrcode-skill-store`), but five crates abbreviate to their product name:

`purrcode-whisker`, `crates/lsp-client` → `purrcode-lsp`. New crates below use the
directory-name-verbatim form, since they carry no product name.

### Created

#### `crates/extension-config` — package `purrcode-extension-config`

**Sits between:** `purrcode-runtime-core` + `purrcode-pawgate` (below) and `purrcode-daemon` +
`purrcode-cli` (above).

**Why a new crate rather than a daemon module:** the policy-precedence chain is already implemented
twice with no shared helper — `effective_policy` (`purrcode-daemon/src/lib.rs:5326`) and
`load_policy` (`crates/purrcode-cli/src/main.rs:3499`) — and they will silently disagree the moment
one grows a project tier. This crate is the shared helper, and it is the only place that reads
untrusted YAML from a repository, so the byte caps, the per-file skip-with-diagnostic behaviour and
the `.purrcode/` path confinement live in exactly one auditable module. It must depend on
`purrcode-pawgate` for `ToolCeiling` derivation, which `purrcode-runtime-core` must not.

**Contents:** `.purrcode/{agents,commands,hooks}/*.yaml` and `.purrcode/settings.yaml` loading for
both the project root and `~/.purrcode/`; `ExtensionSet::restrict`; the three-tier resolver
`Builtin → User → Project`; `AdmissionDiagnostic` production.

**Dependencies to add:** `serde_yaml.workspace = true` (already at `Cargo.toml:81`, currently wired
only into `crates/provider-import`). **UNVERIFIED — implementer must decide:** `serde_yaml 0.9` is
unmaintained upstream and YAML anchors permit billion-laughs expansion. Either switch this crate to
`serde_yaml_ng` / `serde_norway` **before** three loaders depend on it, or cap input bytes before
parse *and* disable aliases. A byte cap mirroring `MAX_INSTRUCTION_BYTES`
(`purrcode-daemon/src/project_context.rs:52`, 16 KiB) is required either way.

#### `crates/project-graph` — package `purrcode-project-graph`

**Sits between:** `purrcode-ninelives` + `purrcode-whisker` + `purrcode-repository-engine` (below)
and `purrcode-agent-runtime` + `purrcode-daemon` (above).

**Why not inside whisker:** whisker's DB is `<worktree>/.purrcode/context.db` — per session
worktree — and `clear_index` (`whisker-context-engine/src/lib.rs:1268`) wipes all eight tables on
every Tier-0 rebuild (`:537`). A project graph stored there dies with the session, which is the exact
opposite of "project intelligence". Whisker also has no migration mechanism, only
`execute_batch(SCHEMA)` at `:433`.

**Why not inside ninelives:** ninelives is the append-only event log and authorization ledger — the
narrowest trust boundary in the system. Giving it tree-sitter, git-subprocess and LSP dependencies
to build graph facts would widen it for no benefit. The graph's *tables* live in the sessions DB via
`migrations/` (registered in ninelives, §6); the graph's *logic* lives here and opens its own
connection to the same file.

**UNVERIFIED — implementer must check:** whether `SessionStore` (`crates/ninelives-recovery/src/lib.rs:100`)
opens the sessions DB in WAL mode with a `busy_timeout`. If not, a second connection from
`purrcode-project-graph` will hit `SQLITE_BUSY` under the daemon's write load, and the graph must
either share the `SessionStore` connection via a new accessor or move to its own file
`<db parent>/graph.db` with its own migrate.

### `migrations/0004_extension_platform.sql`

```sql
-- v1.3 extension platform: descriptor pinning, hook governance, and the
-- capability resolution audit trail. The session event log remains the
-- authoritative record; these tables are queryable projections plus one
-- genuinely durable trust decision (tool_descriptor_pins).

-- Trust-on-first-use pinning for tool descriptors.
--
-- A descriptor discovered from a remote MCP server is authored by that server.
-- Without a pin, a server that reports side_effect_class='read' on Monday and
-- 'destructive' on Tuesday silently changes what PawGate will auto-allow. The
-- pin records the digest the user (or a signed pack) accepted; a descriptor
-- whose digest differs from an approved pin is admitted as Forbidden until
-- re-approved.
CREATE TABLE IF NOT EXISTS tool_descriptor_pins (
    project TEXT NOT NULL,
    tool_id TEXT NOT NULL,
    descriptor_digest TEXT NOT NULL,
    provider TEXT NOT NULL,
    origin TEXT NOT NULL,
    side_effect_class TEXT NOT NULL,
    network_scope TEXT NOT NULL CHECK(json_valid(network_scope)),
    filesystem_scope TEXT NOT NULL CHECK(json_valid(filesystem_scope)),
    approval_policy TEXT NOT NULL,
    first_seen_at TEXT NOT NULL,
    approved_at TEXT,
    approved_by TEXT CHECK(approved_by IS NULL OR json_valid(approved_by)),
    revoked_at TEXT,
    PRIMARY KEY(project, tool_id)
);

CREATE INDEX IF NOT EXISTS idx_tool_descriptor_pins_digest
ON tool_descriptor_pins(project, descriptor_digest);

-- Hook governance. Every hook firing is recorded BEFORE the action is proposed,
-- so a hook that was triggered but denied is distinguishable from one that
-- never fired. action_id links into authorizations(action_id) when the hook
-- reached PawGate.
CREATE TABLE IF NOT EXISTS hook_runs (
    id TEXT PRIMARY KEY,
    session_id TEXT NOT NULL,
    hook_id TEXT NOT NULL,
    hook_digest TEXT NOT NULL,
    trigger TEXT NOT NULL,
    layer TEXT NOT NULL,
    action_id TEXT,

        'triggered','denied','awaiting_approval','executing','succeeded','failed','timed_out','skipped'
    )),
    detail TEXT,
    started_at TEXT NOT NULL,
    finished_at TEXT

CREATE INDEX IF NOT EXISTS idx_hook_runs_session

CREATE INDEX IF NOT EXISTS idx_hook_runs_action
```

- Hook recursion: an `after_write` hook that itself writes does not fire itself (depth guard, tested

- `start_session` with objective `/undo` returns `BadRequest`.

## 9. The permission-ceiling proof

**Claim.** A project-supplied agent, command, hook or skill can never cause an action to execute
under an `ActionConstraints` envelope wider than the workspace ceiling permits.

### 9.1 The lattice, reused verbatim

The proof reuses `SignedPolicyPack::restrict` (`crates/pawgate-runtime/src/lib.rs:326`–`:379`) and
its primitive `field_override` (`:382`–`:388`). Verified semantics, field by field:

| Field | Kind | Combination | Source line |
|---|---|---|---|
| `read_only_programs` | **allow-set** | **intersection** | `:328`–`:337` |
| `approval_required_programs` | **friction-set** | **union** | `:338`–`:347` |
| `denied_argument_fragments` | **deny-set** | **union** | `:348`–`:357` |
| `timeout_seconds` | numeric budget | **min** | `:358`–`:363` |
| `maximum_output_bytes` | numeric budget | **min** | `:364`–`:371` |
| `auto_allow_worktree_writes` | permission bool | **logical AND** | `:372`–`:377` |

**The invariant to copy verbatim: allow-sets intersect, deny-sets union, numeric budgets take the
min, permission booleans AND.** One field with the wrong operator defeats the entire model. A v1.3
`ToolPolicy.allow` that unioned instead of intersected would grant a repository arbitrary tool
access.

`ToolDescriptor::restrict` applies exactly this lattice to the four new axes, all of which are total
orders so the meet is well defined:

```rust
impl ToolDescriptorProposal {
    /// TOTAL: rebuilds every field, so a new descriptor field cannot be
    /// forgotten (the struct literal will not compile).
    fn restrict(self, ceiling: &ToolCeiling) -> (ToolDescriptor, Vec<AdmissionDiagnostic>) {
        // deny beats everything
        if ceiling.denied_tool_ids.contains(self.id.as_str()) { /* → Forbidden */ }
        let side_effect_class = self.side_effect_class.min(ceiling.maximum_side_effect);
        let network_scope     = self.network_scope.meet(&ceiling.maximum_network);
        let filesystem_scope  = self.filesystem_scope.intersect(&ceiling.maximum_filesystem);
        let approval_policy   = self.approval_policy.max(ceiling.minimum_approval);
        // …digest over the RESTRICTED values, never the proposed ones…
    }
}
```

Note the asymmetry: `side_effect_class`, `network_scope` and `filesystem_scope` take the **min /
intersection** (capability shrinks); `approval_policy` takes the **max** (friction grows). A project
file can always ask for *more* approval; it can never ask for less.

### 9.2 The enforcement functions, named

1. **`purrcode_extension_config::ExtensionSet::restrict(self, ceiling: &ToolCeiling) -> ExtensionSet`**
   — applied to every project- and user-layer descriptor at load, before anything is cached.
2. **`purrcode_runtime_core::capability::CapabilityRegistry::admit_tool(proposal, ceiling)`** — the
   **only** function in the workspace that returns a `ToolDescriptor`. `ToolDescriptor` has no public
   constructor, no public field, and no `DeserializeOwned` path that bypasses admission (its
   `Deserialize` impl is used only for reading back already-admitted descriptors from
   `tool_descriptor_pins`, and that read re-checks the digest). This is the load-bearing
   *structural* argument: it is not possible to hand PawGate a descriptor that was not restricted,
   because such a value cannot be constructed.
3. **`purrcode_pawgate::Policy::tool_ceiling(&self, repository) -> ToolCeiling`** — the ceiling is
   derived from the `Policy` that `effective_policy` (`purrcode-daemon/src/lib.rs:5326`) already
   produces. Project config never participates in producing the ceiling; it is only ever restricted
   against it.
4. **`purrcode_pawgate::Policy::evaluate_tool(&self, action, descriptor, repository)`** — the single
   decision point. After PR5 deletes the trust bypass at `purrcode-daemon/src/lib.rs:3863`–`:3876`,
   there is no path to an `ActionConstraints` that did not come out of this function.
5. **`ninelives::SessionStore::authorize` / `consume_authorization`**
   (`crates/ninelives-recovery/src/lib.rs:179`, `:258`) — the constraints are bound into
   `ProposedAction::digest_v3(action, constraints, descriptor_digest)` and the capability is
   single-use, enforced by `consumed_at` and the `action_id` PRIMARY KEY at
   `migrations/0001_initial.sql:22`.
6. **`claw::ToolRuntime::execute`** (`crates/claw-sandbox/src/lib.rs:84`) — re-derives the digest
   (`:90`), consumes (`:91`) and re-checks constraint equality (`:92`) before spawning. Widening
   between authorization and execution is impossible.

### 9.3 The chain of custody

```
project YAML (untrusted bytes)
   │  ExtensionSet::load          ← byte cap, path confinement, per-file skip
   ▼
ToolDescriptorProposal            ← a CLAIM. Cannot be executed.
   │  ExtensionSet::restrict / CapabilityRegistry::admit_tool(ceiling)
   ▼                                 ← the ONLY mint. Lattice meet on 4 axes.
ToolDescriptor                    ← no public constructor, no public field
   │  Policy::evaluate_tool(action, descriptor, repository)
   ▼                                 ← schema validation, then decision
JudgmentDecision + ActionConstraints
   │  apply_permission_mode(mode, decision, descriptor)   ← see 9.4
   ▼
SessionStore::authorize           ← digest_v3(action ‖ constraints ‖ descriptor_digest)
   ▼
ToolRuntime::execute              ← digest re-derive + consume + constraint equality
   ▼
sandbox profile                   ← ActionConstraints is the enforced envelope
```

Every arrow is total and every arrow narrows. There is no arrow from project YAML to
`ActionConstraints` that skips `admit_tool`.

### 9.4 Two holes that must be closed in the same change, or the proof is false

**Hole A — `apply_permission_mode`.** `crates/agent-runtime/src/normalize.rs:377`–`:397` runs
*after* `Policy::evaluate` and after the contextual judge. Under `PermissionMode::Auto` — **the
default** — every `RequireApproval` silently becomes `AllowWithConstraints` (`:385`); under
`FullAccess` even a `Deny` becomes `AllowWithConstraints(read_only(worktree))` (`:388`–`:393`).
Since PawGate returns `RequireApproval` for every external tool today (`pawgate-runtime/src/lib.rs:197`),
unifying MCP onto the native path under `Auto` would **auto-approve every MCP tool call with no
prompt**. Required, in PR4:

- `apply_permission_mode` takes `&ToolDescriptor`.
- `Auto` may downgrade `RequireApproval` **only** when
  `descriptor.approval_policy() <= ApprovalPolicy::ByClass` **and**
  `descriptor.side_effect_class() == SideEffectClass::Read` **and**
  `matches!(descriptor.network_scope(), NetworkScope::None)`.
- `FullAccess` **never** converts `Deny` into an allow. A checked-in project file must not be able
  to overrule an explicit organizational `Deny`, and a session mode a human set for convenience must
  not either.

**Hole B — there is no ceiling above the repository in the default install.** With no
`[organization_policy]` in `config.toml`, `effective_policy`'s else-branches
(`purrcode-daemon/src/lib.rs:5338`–`:5340`) load `<repository>/policies/default.toml`
(`resolve_policy_path`, `pawgate-runtime/src/lib.rs:701`) or fall back to `Policy::default()`.
**Cloning a hostile repository whose `policies/default.toml` sets `auto_allow_worktree_writes = true`,
empties `denied_argument_fragments` and adds programs to `read_only_programs` already widens the
runtime today, with no signature and no prompt.** An `AgentProfile` restricted against *that* is
restricted against nothing.

Required, in PR3: a **machine-level user tier** that the project tier is restricted against.

```rust
/// v1.3 precedence. Three tiers instead of two.
///   Policy::default()                       ← the floor
///     ↓ restrict_local(base, user)          ← ~/.purrcode/policy.toml (or config.toml [policy])
///     ↓ restrict_local(base, project)       ← <repo>/policies/default.toml — RESTRICTED, not replacing
///     ↓ SignedPolicyPack::restrict(base)    ← org pack, unchanged, still the outermost authority
pub fn load_effective_v3(
    user_policy: Option<&Path>,
    repository_policy: Option<&Path>,
    organization: Option<(&Path, &str)>,
) -> Result<Policy, PolicyError>;
```

`restrict_local` is `SignedPolicyPack::restrict`'s lattice with `allowed_overrides` **empty** — the
project tier gets no `field_override` escape hatch at all, because `field_override` returns the
local value *verbatim* with **zero clamping** when a field is delegated (`pawgate-runtime/src/lib.rs:383`–`:384`),
and unlike the org pack a project's delegation list would not be signed. Delegation stays a
signed-org-pack-only feature.

Both `effective_policy` (`purrcode-daemon/src/lib.rs:5326`) and `load_policy`
(`crates/purrcode-cli/src/main.rs:3499`) must call it, or the CLI and daemon will disagree about
effective permissions for the same repository.

### 9.5 What is verified vs. what the implementer must check

- **Verified:** `restrict` is private (`fn restrict`, no `pub`, `pawgate-runtime/src/lib.rs:326`) —
  PR2 must make it `pub`. `verify` (`:267`–`:314`) is fail-closed and checks expiry, the
  `allowed_overrides` subset against six hardcoded literals (`:276`–`:283`), a blake3 payload hash
  over the canonical `SignedPayload` (`payload_bytes`, `:316`–`:324`), and Ed25519 `verify_strict`.
  Because `allowed_overrides` sits inside the signed payload, the delegation list is itself
  tamper-evident — **that property must be preserved.**
- **Verified:** `ApprovalAuthority::SignedPolicy { policy_id }` (`runtime-core/src/lib.rs:748`) is
  never constructed. A signed tool registry is its natural first producer; PR5 should stamp it.
- **UNVERIFIED — implementer must check `NetworkScope::Hosts` enforcement.** Claw refuses
  `network: true` outright (`claw-sandbox/src/lib.rs:519`, `:673`); the stdio MCP sandbox grants
  `(allow file-read*)` over the whole filesystem and `(allow process*)`
  (`mcp-host/src/lib.rs:726`–`:727`, Linux `--ro-bind / /` at `:748`); HTTP transport
  (`mcp-host/src/lib.rs:551`–`:605`) gets **no sandbox, no memory limit and no filesystem
  confinement at all**, and `memory_limit_bytes` is only enforced on Linux (`:691`–`:706`) — on
  macOS it is decorative. So `NetworkScope::Hosts` and `FilesystemScope` are, for the MCP provider,
  **descriptions of a bound that is not enforced by the sandbox**. Either implement host filtering
  in the provider adapter and say so in the descriptor, or restrict every MCP descriptor's
  `network_scope` to `None | Any` and require `AlwaysAsk` for `Any`. Do not ship a `Hosts` variant
  the runtime does not honour — that is exactly the declared-but-unenforced pattern (`ScoutRequest.
  allowed_action_kinds`, `agent.rs:124`) this design exists to eliminate.
- **UNVERIFIED — implementer must check the four independent authorization implementations.** Beyond
  the native and MCP paths there are process-local `consumed_authorizations: HashSet<String>` in
  `crates/web-research/src/lib.rs:206`/`:444`–`:457` and the identical construct in
  `crates/skill-registry/src/lib.rs:647`/`:749`. These do **not** survive a daemon restart, unlike
  the durable `consumed_at` column (`migrations/0001_initial.sql:28`). Any "one authorization path"
  claim that ignores these two leaves replay protection inconsistent across restarts; PR5 should
  fold both onto `SessionStore::consume_authorization`.

## 10. Backward compatibility

### 10.1 v1.2 contracts that must keep working

**`GET /v1/commands` JSON shape.** The IDE parses it at `crates/purrcode-ide/src/model.rs:1673`–`:1692`
into `{ name, description, group, execution: { kind, path?, prompt? } }`, with an `Unknown` variant
(`:1657`–`:1660`) for unrecognized kinds. Rules:
- Adding fields is safe (unknown fields are ignored).
- **A new `kind` value is not safe in practice.** `Unknown` commands still appear in `/` completion
  (`crates/purrcode-ide/src/app/composer.rs:112`–`:138`) and the ⌘⇧P palette
  (`app/mod.rs:2807`–`:2814`), then fail on dispatch — a false affordance of exactly the class
  `af3ae5b` and `3e43e67` were written to close.
- **Therefore `CommandExecutionSpec::Agent` is serialized to the wire as
  `Daemon { method: "POST", path: "/v1/sessions/{id}/commands/<name>" }`.** A v1.2 IDE dispatches it
  correctly with zero client changes, and the daemon owns the route so a project file never declares
  a path. This is both the compatibility story and the security fix.
- Query params on `GET /v1/commands` must be **optional**; omitting them returns exactly today's
  built-in list.

**`POST /v1/sessions/{id}/mcp`** (`purrcode-daemon/src/lib.rs:504`) keeps its request and response
shape (`{ requires_approval, action_id, action_digest }` on the propose leg, `:3930`). Reimplemented
over the generic path; the IDE's MCP panel must not need a change in the same release.

**`SessionEvent` serde tags.** Every existing variant name and payload shape is frozen — the reducer
(`runtime-core/src/lib.rs:1582`) replays historical logs, `EvidenceBundle::export_bundle`
(`evidence-bundle/src/lib.rs:79`) replays `store.timestamped_events`, and checkpoint/fork
(`0003_session_workspace.sql`) depend on replay. New variants go **at the end of the enum**.
**Forward compatibility does not hold**: a v1.3-written log opened by a v1.2 binary will fail to
deserialize the new variants. Version-gate the daemon/IDE handshake, or accept that downgrade is
not supported and say so in the release notes.

**`ProposedAction` serde.** Adding `Tool` is additive for reading old payloads. `ExternalTool`

**`ProposedAction::digest`.** The v1.2 two-element hash must remain callable for
`ExternalTool`/legacy actions, because outstanding authorizations in an existing `sessions.db` were
written with it. `digest_v3` is used only for `ProposedAction::Tool`. **UNVERIFIED — implementer
must check** whether any in-flight authorization can straddle the upgrade; if so, the daemon must
re-derive with the v1.2 function when the row predates migration 4.

**`SessionControls`** (`runtime-core/src/adaptation.rs:1028`) shape is frozen; the IDE settings page
and `validate_supported_controls` (`purrcode-daemon/src/lib.rs:2264`) both depend on it. A
command-declared profile must be validated by the **same** `validate_supported_controls` and must
never widen `permission_mode` — it is documented as a request from an authenticated human that the
model can never set (`adaptation.rs:1038`–`:1043`).

**`WorkerSpec`** (`supervisor-runtime/src/lib.rs:52`) gains `profile: Option<String>` as
