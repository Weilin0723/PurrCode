# v0.5.1 connection recovery

v0.5.1 corrects three failures reproduced on an 8 GB Apple Silicon Mac after the v0.5.0
release.

## Root causes

- The cross-platform keyring wrapper selected the macOS User-domain keychain. On the affected
  account, that API returned `errSecNoSuchKeychain` even though the default login keychain was
  healthy and writable.
- The TUI discarded the daemon's bounded credential-store error and rendered only a generic
  rejection.
- First-run Ollama discovery sorted model names and selected the first one. That chose
  `llama3.1:8b`; a four-token native request took about 37 seconds on the target machine and
  exceeded the 30-second connection-probe deadline.
- First-run configuration did not persist discovered model capability entries, so the provider
  review screen could report no discovered models.

## Corrections

- macOS credentials use the actual default login keychain returned by
  `SecKeychainCopyDefault`; other platforms retain their native keyring backends.
- Credential failures preserve the daemon's redacted diagnostic text.
- On systems with at most 16 GB memory, first-run configuration selects the smallest model using
  observed Ollama size metadata and enables single-model coder/judge mode.
- Ollama profiles persist the native API root and every model observed through `/api/tags`.

## Real-environment evidence

- A disposable credential completed a Keychain write/read/delete round trip.
- The authenticated daemon `/v1/credentials` endpoint returned HTTP 200 and its disposable entry
  was deleted.
- Fresh initialization selected `ollama/llama3.2:1b` for coder and judge, listed all six installed
  models, used `http://127.0.0.1:11434/`, and did not load a model.
- The real Ollama provider connection probe returned HTTP 200 with semantic output.
- The provider-backed multi-turn streaming integration test passed against `llama3.2:1b`.
- After each test, `/api/ps` returned an empty model list.
