## 1. Defect A — Settings is a shell (P0)

### 1.1 Observed

The Settings window offers eight pages. MCP servers, skills, fast model configuration and Codex
linking are all absent. Nothing found through "Find a setting" is a setting.

### 1.2 Root cause (verified)

`SettingsPage` has 8 entries (`crates/purrcode-ide/src/app/settings.rs:47`) and
`settings_content` dispatches to 8 render functions (`settings.rs:230`). **Only one of them talks
to the daemon.**

- `settings_models` (`settings.rs:353`) is the sole page issuing `self.client.send(...)`.
- `settings_general` (`settings.rs:306`) mutates local egui theme state only.
- `settings_advanced` (`settings.rs:597`) flips one boolean.
- Authority (`514`), Agent (`531`), Context & skills (`548`), Terminal & Git (`562`), Privacy (`583`)
  contain **zero** daemon calls. They are `ui.label(...)` over already-loaded session fields plus
  hard-coded prose.

Per named gap:

1. **MCP** — the IDE has no MCP code at all. The daemon has no MCP *management* route either; only
   `POST /v1/sessions/{id}/mcp` for invocation (`purrcode-daemon/src/lib.rs:463`). Servers are read
   from the app-config TOML `extensions["mcp"].servers` at invoke time (`lib.rs:2818`). **Routes must be added.**
2. **Skills** — the daemon already serves nine skill routes (`lib.rs:528-540`) and the TUI drives all
   of them (`purrcode-tui/src/skill_browser.rs:44`, `command_palette.rs:855`). The IDE's
   `daemon.rs` has no `Request` variant for any of them.
3. **Quick model config** — the daemon serves the whole local-model/Ollama lifecycle
   (`lib.rs:492-526`); the TUI drives all of it (`command_palette.rs:198`). The IDE exposes only
   `ListModels`, `SetModel`, `AssignModelRole`, `ConfigureProvider`.
4. **Codex** — `purrcode-daemon` has zero references to codex. `purrcode-codex-bridge` is a
   dependency of `purrcode-cli` only, reachable through `purrcode codex doctor|run`
   (`purrcode-cli/src/main.rs:1648`). **Routes and a Cargo dependency must be added.**

Two secondary defects on the same surface:

- **Settings never refreshes.** Opening it (`mod.rs:1312`, `1357`) triggers no fetch;
  `Request::ListModels` is sent once in `PurrCodeIde::new` (`mod.rs:546`).
- **`ConfigureProvider` hardcodes `"replace": false`** (`daemon.rs:1192`), so editing an existing
  provider is *always* rejected with `provider profile 'X' already exists` (`lib.rs:6129`). The add-
  provider form is write-only and unrecoverable.
- **Search filters page labels only** (`settings.rs:244`), so "Find a setting" cannot find a setting.

### 1.3 Requirements

**FR-A1 — Settings loads its own data.** Opening Settings, and switching to a page, dispatches the
queries that page renders. No page may render a control whose value was never fetched.

**FR-A2 — Models & providers becomes operable.**
- List providers (`GET /v1/providers`), show each one's configured models (`GET /v1/providers/{name}`),
  test one (`POST /v1/providers/test`), remove one (`DELETE /v1/providers/{name}`).
- Discover local models (`POST /v1/providers/discover` with `{"provider_type":"ollama"|"lm-studio"}`).
- Editing an existing provider must send `replace: true`. `Request::ConfigureProvider` grows a
  `replace: bool` field; the form sends `true` when the name already exists.
- Role assignment must offer every role, not just `coding_worker`. The role list comes from
  `GET /v1/bootstrap` → `control_capabilities`, already fetched into `self.bootstrap`.
- Credentials remain out of scope for the IDE: keychain **reference names** only, as today
  (`settings.rs:444`). `POST /v1/credentials` is not called from the IDE.

**FR-A3 — Local models page (the "quick config" ask).**
- Status card from `GET /v1/local-models`: reachability, installed models, loaded models, memory
  pressure.
- Recommendations from `GET /v1/local-models/recommendations`, rendered as qualification cards with
  their stated risks — never as a bare "recommended" badge.
- Actions: qualify (`POST /v1/local-models/qualify`, needs a multi-minute client timeout), unload
  (`POST /v1/local-models/unload`), and the pull flow.
- **Pull is a four-step approval flow and must stay one:** `propose` → `approve` → `start` → poll
  `GET /v1/local-models/pull/{action_id}` until terminal, with `cancel` available throughout. Poll
  the JSON route; the SSE route (`/events`) is unusable from the IDE's blocking client.
- Lifecycle policy editor over `GET|POST /v1/local-models/settings`
  (`unload_after_request` | `idle_timeout` | `keep_loaded` | `external`; `idle_timeout_seconds`
  constrained to `30..=86400`).

**FR-A4 — Skills page.**
- List installed skills (`GET /v1/skills` → `SkillRecord`), showing scope, publisher, signature
  status, qualification status and use counts. Remove one (`DELETE /v1/skills/{id}`).
- Search/download/install are session-scoped and approval-gated on the daemon
  (`POST /v1/skills/search`, `/download`, `/install/propose`, `/install/{action_id}/approve`,
  `/install`). The IDE must reproduce the full gate, not skip to `install`. When no session is
  selected these controls are disabled with the reason stated, because `session_id` is required.
- Block a publisher (`POST /v1/skills/publishers/block`).

**FR-A5 — MCP page.** Requires new daemon routes (§1.4). The page lists configured servers with
program, arguments, working directory, network flag and limits; adds and removes them; and runs a
discovery probe per server via the existing `POST /v1/sessions/{id}/mcp` with `tool: "__discover__"`,
which is permitted even in read-only task modes (`lib.rs:2757`). Secret values are never shown or
entered — only `environment_from` variable *names*, matching `purrcode.toml.example`.

**FR-A6 — Codex page.** Requires new daemon routes (§1.4). Shows `[codex]` config
(`enabled`, `binary`, `execution_mode`, `timeout_seconds`, `inherit_auth`,
`require_final_diff_judgment`, `allow_active_tree_write`), a "Check Codex" action returning
`CodexDoctorReport`, and an enable/disable toggle. If the binary is missing, say so and name the
path that was tried.

**FR-A7 — Search finds settings, not pages.** Each control registers a keyword set; the search field
filters controls and jumps to the owning page. A query matching nothing says so.

**FR-A8 — Failures are visible.** Every settings mutation renders its daemon error inline next to the
control that produced it. A rejected `ConfigureProvider` must never look like a no-op.

### 1.4 Daemon work required

| Route | Method | Purpose |
|---|---|---|
| `/v1/mcp/servers` | `GET` | List `extensions["mcp"].servers` from app config |
| `/v1/mcp/servers` | `POST` | Add/replace one server (`McpServerConfig`) |
| `/v1/mcp/servers/{id}` | `DELETE` | Remove one server |
| `/v1/codex` | `GET` | Current `[codex]` table |
| `/v1/codex` | `POST` | Update `[codex]` table |
| `/v1/codex/doctor` | `POST` | Run `CodexBridge::doctor` → `CodexDoctorReport` |

`crates/purrcode-daemon/Cargo.toml` gains `purrcode-codex-bridge`. All six routes go through
`authorize(&state, &headers)?` like every other route. MCP server writes must reject any payload
carrying a literal secret, reusing `reject_secret_content` (`lib.rs:2220`).

### 1.5 Design direction

The user cited `nousresearch/hermes-agent` and `anomalyco/opencode` as references and the
`frontend-design` skill. Translated to an egui surface, the binding rules are:

- **One dominant surface colour, sharp accent.** Accent is for state and the single primary action
  per page — never as a decorative tile (this is the same rule that produced defect #2).
- **Density is a decision, not an accident.** Settings is a dense, list-first surface: rows, not
  cards-inside-cards. Reserve `tokens.card()` for a genuine group, not for every row.
- **Every page opens with a status line, then controls.** Prose that is not attached to a control is
  deleted, not reformatted. This is what removes the five prose-only pages.
- **Nothing carries meaning by colour alone** (existing PRD §32) — a qualification risk, an unreachable
  provider and a blocked publisher all state their status in words.
- Navigation groups become `WORKSPACE / MODELS / EXTENSIONS / RUNTIME / SYSTEM` to make room for
  Local models, Skills, MCP and Codex.

### 1.6 Acceptance criteria

- With Ollama running, a user configures a local model and assigns it a role without touching a
  terminal or a TOML file.
- A skill can be listed, inspected and removed; installing one walks the approval gate and shows the
  qualification result.
- An MCP server can be added, listed, probed and removed; restarting the daemon preserves it.
- `Check Codex` reports a real doctor result, including the exact binary path when it is missing.
- Re-saving an existing provider succeeds instead of erroring.

## 2. Defect B — Follow-up turns are rejected and answers miss the request (P0)

### 2.1 Observed

After the first answer the session reads **Ready**. The user sends `please explain`. It renders as a
user bubble, an activity card appears reading `Interrupted with z-ai/glm-5.2`, state flips to
**Working**, and no answer ever arrives. Separately, the first turn's "answer" was
*"I have gathered sufficient evidence … to provide a comprehensive explanation"* — a progress report,
not an explanation.

### 2.2 Root causes (verified)

These are four distinct defects that compound. Each needs its own fix.

**B-1 — `Interrupted with <model>` is a presentation relabel, not an error.**
`crates/purrcode-daemon/src/lib.rs:4343`:

```rust
if ended {
    items[position].status = ActivityStatus::Failed;
    items[position].label = items[position].label.replacen("Thinking", "Interrupted", 1);
}
```

A `ModelRequestStarted` produces `Thinking with {model}` (`lib.rs:4216`) and a matching finish
rewrites it to `Thought with {model}` (`lib.rs:4228`). If the turn window reaches
`SessionCompleted | SessionFailed | SessionCancelled` with that item unfinished, it is relabelled
`Interrupted` and marked failed. The card therefore carries **no reason, no remedy and no
distinction** between a real cancel, a provider error and a bookkeeping gap — and it is emitted for
the *previous* turn while the new one starts, which is why it appears to be a response to the
follow-up.

**B-2 — A follow-up on a worktree-less session re-runs the original objective.**
`append_message` (`lib.rs:1979`):

```rust
let operation = if awaiting_plan_review(&session) {
    AgentOperation::RevisePlan { feedback: content.to_owned() }
} else if session.worktree.is_none() {
    AgentOperation::Start          // <-- ignores `content`
} else {
    AgentOperation::Resume
};
```

`AgentOperation::Start` calls `agent.start_initialized(...)` (`lib.rs:3666`), which runs the
**session objective**. A read-only session ("Explain this codebase…") never creates a worktree, so
the follow-up text is durably recorded in the conversation and then thrown away by the operation
selection. The agent restarts the original question. `RevisePlan` is the only branch that carries the
user's words into the operation, and it says so in its own doc comment (`lib.rs:3143`) — the same
guarantee is missing for an ordinary follow-up.

**B-3 — A follow-up can be refused with no visible reason, while the UI shows Working.**
`append_message` returns `409 Conflict` for `this session cannot accept a follow-up message`
(`lib.rs:1964`), and `spawn_agent_operation` returns `409` for
`session already has an active daemon lease` (`lib.rs:3174`) and
`session cancellation or pause is still settling` (`lib.rs:3158`). The IDE clears the composer and
sets `submitting = true` **before** any reply (`app/mod.rs:648-670`); the failure path is
`reply_submission_failure` (`daemon.rs:941`). Any gap in that path leaves the composer empty, the
state Working, and the user with no message.

**B-4 — The assistant's answer *is* the model's rationale field.**
`crates/agent-runtime/src/agent.rs:1707-1740` promotes `turn.rationale` verbatim as the assistant
`ConversationMessage`. `completion_needs_repair` (`schema.rs:382`) exists to catch exactly the
observed failure and escalates through two repair prompts (`agent.rs:1558-1600`) before failing the
turn. It is a **hand-maintained substring blocklist** — ~90 markers across
`progress_markers` / `imperative_prefixes` / `readiness_markers`. Any phrasing outside that list
passes, and every miss ships as a finished answer.

### 2.3 Requirements

**FR-B1 — A follow-up always carries its own text into the operation.**
Add `AgentOperation::Continue { message: String }` (or extend `Resume` with an optional message) and
select it for every non-plan-review follow-up, regardless of whether a worktree exists. The
worktree-less case initialises lazily *and* answers the follow-up; it must never silently re-run the
original objective. Mirror the existing `RevisePlan` guarantee and document it the same way.

**FR-B2 — `Interrupted` states why.** The relabel at `lib.rs:4343` must distinguish:
- provider/transport failure → `Model request failed` + the recorded reason,
- explicit cancel → `Cancelled by you`,
- terminal state with no finish event → `Model request did not complete`,
and must carry a `summary` the IDE can render. A card that says only "Interrupted" with a model name
is not evidence.

**FR-B3 — A refused follow-up is never silent.** On any submission failure the IDE must restore the
draft text into the composer, clear `submitting`, and show a notice naming the daemon's reason and the
action that clears it (wait for the current turn, resume the paused session, start a new session).
`pending_submission` (`app/mod.rs:649`) already exists for the restore; the notice must be mandatory,
not best-effort.

**FR-B4 — The workbench never shows Working without something running.** The state view and the
activity presenter must be derived from one source. If the last activity item is failed and no lease
is held, the header says so.

**FR-B5 — Completion validation stops being a substring blocklist.** Replace/augment
`completion_needs_repair` with a check that does not depend on enumerated phrasings. Minimum bar:
a `complete: true` turn whose rationale contains no reference to any artifact the turn actually read
(no file path, symbol, command or quoted evidence from the session's own action log) is a progress
report. Keep the existing markers as a fast path; add the evidence-grounding test as the backstop, and
keep the two-attempt repair escalation. Record every repair in the durable log so the failure rate is
measurable rather than anecdotal.

**FR-B6 — Advice-only sessions get a real answer contract.** For an objective classified by
`objective_requests_advice_only` (`schema.rs:~330`), the final turn must be the answer itself. The
existing behaviour of appending `Proposed plan:` steps to the rationale (`agent.rs:1707-1719`) is kept,
but only when the rationale already passes FR-B5.

### 2.4 Acceptance criteria

- On a read-only session that has answered, `please explain` produces an answer to *that* question.
  A transcript replay proves the follow-up text reached the agent operation.
- Sending a follow-up while a turn is running either queues it or refuses it with a named reason and
  the text still in the composer. It never empties the composer into silence.
- No transcript ever contains a bare `Interrupted with <model>` card without a reason.
- A regression test feeds the exact observed string — *"I have gathered sufficient evidence from the
  architecture documentation, workspace manifests, and key source files (main.rs for both the CLI and
  the daemon) to provide a comprehensive explanation of the codebase and identify its entry points."*
  — and asserts it is rejected as a completion.
- A second test asserts a genuine answer containing file paths and findings is **not** rejected.

## 3. Defect C — Change review shows no per-file counts (P1)

### 3.1 Observed

The right-hand panel titled **Changes** lists bare folder names under a **FILES** heading, with no
`+N / −M` anywhere, while the status bar says **160 uncommitted files**.

### 3.2 Root cause (verified)

**C-1 — The panel titled "Changes" is not the changes panel.** The aux title strip hard-codes
`"Changes"` for `AuxView::Source` (`app/mod.rs:1472`) and its body calls `code_column`
(`mod.rs:1501`). `code_column` dispatches on a *different* field, `self.code_panel`
(`app/code.rs:22`), which is initialised to `CodePanel::Source` (`mod.rs:508`) and reset to
`CodePanel::Source` on every `open_workspace` (`mod.rs:710`). With no file open it renders
`code_file_tree` — heading "Files", uppercased to "FILES" by `section_heading` (`mod.rs:1209`) — which
is exactly the screenshot. **The only assignment of `CodePanel::Changes` in the whole crate is inside
`changed_file_row` (`code.rs:281`)** — you must already be looking at a changed-file row to reach the
changes view. Nothing binds a shortcut to it either, so the `⌘2` hint printed at `code.rs:42` does
nothing.

**C-2 — Even when reached, the panel can only describe a session worktree.** `changes_panel` reads
only `self.session.changes` (`code.rs:192`), fed by `GET /v1/sessions/{id}/changes?scope=agent`
(`daemon.rs:1230`). The daemon returns `{"status":"unavailable", …, "files":[]}` whenever
`session.worktree` is `None` (`lib.rs:4818`), and `parse_changes` maps that to `available: false`
(`model.rs:826`). `changes_panel` then **silently swaps in the file tree** (`code.rs:193`) — the same
visual as C-1, with no statement that nothing was checked. All three `ChangeScope` values are
evaluated with `cwd = worktree.path` (`repository-engine/src/lib.rs:315`), so **no scope the UI can
select ever describes the user's own checkout.**

**C-3 — The daemon is not the problem.** `session_changes` does emit
`entries: [{path, status, additions, deletions}]` with real numstat (`lib.rs:4847`), computed by
`git diff --numstat -z` + `--name-status -z` (`repository-engine/src/lib.rs:341`), with untracked
files enumerated via `git ls-files --others --exclude-standard -z` (`lib.rs:394`). The IDE parser
reads `additions`/`deletions` correctly (`model.rs:793`). `Changes::summary()` already formats
`"N files · +A −D"` (`model.rs:236`) **and is never called**.

**C-4 — The status bar reads a different, count-only source.** `bar.rs:353` prints
`workspace_state.changed_file_count`, parsed at `mod.rs:223` from `GET /v1/workspace`, which is a
`git status --porcelain=v1` line count on the user's real repository (`lib.rs:5011`). It returns a
scalar only. **No daemon route returns per-file numstat for a plain workspace folder.**

**C-5 — Two rendering bugs on top.** `changed_file_row` gates both counts on
`if let (Some(add), Some(del))` (`code.rs:258`), so a file with one known and one unknown count shows
neither. `render_tree_level` marks a file changed by comparing **basenames only** (`code.rs:132`), so
one changed `mod.rs` dots every `mod.rs` in the tree, and it shows a bullet, never a number.

### 3.3 Requirements

**FR-C1 — New daemon route: `GET /v1/workspace/changes?repository=<path>&scope=working_tree|staged`.**
Response shape identical to `session_changes` minus the `worktree` block, so the existing
`parse_changes` is reused unchanged. Implementation: extract the git plumbing out of the session-only
`RepositoryEngine::changes` into a `change_set_at(root, base, staged_only)` helper, and add
`workspace_changes(repository, scope)` that calls it without `ensure_session_path`
(`repository-engine/src/lib.rs:309` guards session paths and must not be reused for a workspace).

**FR-C2 — `session_changes`' unavailable branch gains `"entries": []`** (`lib.rs:4821`) so no client
ever sees a payload where `files` exists and `entries` does not.

**FR-C3 — The panel titled Changes shows changes.** `code_column` defaults to `changes_panel` when no
file is open. The aux title strip stops labelling a source file "Changes" (`mod.rs:1472`).

**FR-C4 — Session and workspace changes are both shown, and labelled.** Not one silently replacing the
other. Two groups: **Agent changes** (session worktree) and **Your uncommitted changes** (the open
folder). A user must never have to guess which tree a row describes — this is the existing PRD §14
requirement applied to the change list.

**FR-C5 — Per-file counts render independently.** `+N` and `−M` are emitted separately, right-aligned;
a file with no numstat says `binary` rather than showing nothing. The aggregate `changes.summary()`
line is rendered at the top of the list.

**FR-C6 — Nothing falls back silently.** When a change set is unavailable the panel says so and offers
a retry; the file tree may follow *below* that statement, never instead of it. `Request::RetryPanel`
already exists in the transport (`daemon.rs:79`) and is currently never constructed.

**FR-C7 — The file tree marks changed files by path, with counts.** Replace the basename comparison
(`code.rs:132`) with a repo-relative path index built once per frame from both change sets.

**FR-C8 — One number, one source.** The status bar prefers `workspace_changes.files_changed` once
available, and appends `+A −M`. If the porcelain count is kept as the fallback, it must use
`--untracked-files=all` (`lib.rs:5008`) so an untracked directory is not counted as one file in the
status bar and as many files in the list.

**FR-C9 — Source Control sidebar (⌘4) uses the same data.** `source_control_panel` (`mod.rs:1421`)
has the identical gate and prints a bare "No changes" while the status bar says 160. It gets the same
treatment.

### 3.4 Cost note

`git diff --numstat` + `--name-status` over ~160 dirty files on every workspace poll is not free. The
workspace-changes route should skip the binary patch entirely (the panel needs numstat and
name-status only) and cache on the porcelain digest. Poll at the existing 4 s workspace cadence, not
the 700 ms session cadence.

### 3.5 Acceptance criteria

- Opening the aux panel on a repository with uncommitted work shows a per-file list with `+N −M`
  and an aggregate line, without selecting a session.
- The number in the status bar and the number of rows in the panel agree.
- With an agent session running, agent changes and the user's own uncommitted changes are both
  visible and separately labelled.
- A binary file appears in the list, marked `binary`, rather than silently having no counts.
- Two files named `mod.rs`, one changed, produce exactly one marked row in the tree.

## 4. Cross-cutting: the design language

Applies to all three defects, and to the two already fixed.

1. **The accent colour marks state and one primary action. It is never a backdrop.** Defect #2 was a
   `rect_filled` behind the mascot; the same instinct produces accent-tinted rows and pill soup.
2. **A surface states its own status before it offers controls.** Every silent fallback in this
   document (`code.rs:193`, `mod.rs:1421`) is the same bug: showing plausible content instead of
   saying nothing was checked.
3. **No control renders a value that was never fetched.** This is FR-A1, and it is what makes the
   Settings pages honest.
4. **Words, not colour, carry meaning** — already PRD §32, repeatedly violated by bare dots and bare
   status letters.
5. **Density over decoration.** Settings and change review are list surfaces. Card-in-card nesting is
   the failure mode to avoid.

## 5. Sequencing and test plan

**Order.** B (correctness) → C (change review) → A (settings breadth). A is the largest and the least
likely to be wrong in a way that costs a user their work.

**Verification before any of it lands:**

```bash
cargo test -p purrcode-ide -p purrcode-daemon -p purrcode-agent-runtime -p purrcode-repository-engine
```

**New tests required**

| Requirement | Test |
|---|---|
| FR-B1 | A worktree-less session receiving a follow-up runs an operation carrying the follow-up text |
| FR-B3 | A 409 from `append_message` restores the draft and raises a notice |
| FR-B5 | The observed meta-answer string is rejected; a grounded answer is accepted |
| FR-C1 | A temp repo with one modified + one untracked file returns populated `entries[*].additions` |
| FR-C3 | `code_column` selects `changes_panel` when `open_files` is empty |
| FR-C7 | Two same-named files, one changed, mark exactly one tree row |
| FR-A2 | Re-saving an existing provider with `replace: true` succeeds |
| #4 (landed) | A poll response `{"chunk":{"bytes":[…],"next_offset":n}}` reaches the emulator and advances the offset to `n` |

## 6. Open decisions

1. **Follow-up while running** — queue it, or refuse it? Refusing is honest and cheap; queueing is
   what users expect from a chat surface. Refusing is specified above; queueing requires a durable
   pending-message slot on the session.
2. **`ChangeScope::Workspace` end-to-end** vs. a separate workspace route. `ChangeScope::parse`
   currently returns `Agent` for any unknown string (`repository-engine/src/lib.rs:90`) — a silent
   fallthrough that should become an error either way. A real `Workspace` variant is cleaner but
   touches the shared contract crate.
3. **Terminal transport** — keep the 120 ms poll, or add `GET /v1/terminals/{id}/stream` (SSE)?
   Polling caps keystroke echo at ~120 ms + RTT per terminal.
4. **MCP config ownership** — the daemon writes `purrcode.toml`, or the IDE does? Daemon-owned is
   consistent with providers and models, and keeps one writer for the file.
5. **Skills without a session** — every skill install route requires `session_id`. Either Settings
   disables install until a session exists, or the daemon grows a workspace-scoped install path.
