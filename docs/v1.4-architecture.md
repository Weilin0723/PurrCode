# PurrCode v1.4 — Collaborative Agent Development

**Bounded multi-agent delegation with evidence-gated integration.**

v1.3 made PurrCode extensible: *make PurrCode yours*. v1.4 makes those
extensions cooperate safely: *specialists can work together without giving up
control*.

This document describes what was built, where each piece lives, and — in the
last two sections — what is deliberately not built and what is not yet proven.

---

## 1. The two invariants

Everything else in v1.4 is an implementation detail of these.

### Delegation never creates authority

```text
Effective worker authority
    = workspace policy ∩ parent agent ceiling ∩ specialist profile
      then narrowed to the delegated paths
```

This is structural, not conventional. [`Delegation`] has **no public
constructor**; the only way to obtain one is [`DelegationRequest::admit`], which
performs the fold above and returns an error rather than a delegation when the
result would exceed any input. A delegation carrying authority nobody granted
cannot be constructed, so no call site can forget to check.

Two subtleties are load-bearing:

- **Narrowing is not intersection.** `FilesystemScope::intersect` is
  exact-string on globs (a v1.3 decision, conservative by design), so
  `src/auth/**` ∩ `**` is *empty*. Using it for a delegated path scope would
  silently turn every writer into a reader. `narrow_to_paths` instead keeps each
  requested pattern that some ceiling glob *covers*, which can only shrink
  authority. `glob_covers` is syntactic and refuses when unsure.
- **A writer under a read-only parent is refused, not downgraded.** Admitting a
  `Patch` delegation with no write authority would produce a worker that cannot
  do its job and whose empty result would read as success.

Verified by a generated sweep over ceiling combinations
(`admitted_authority_is_within_every_input_over_a_generated_sweep`) and, at
runtime, by `Policy::evaluate_delegated`.

### Workers propose, evidence proves, the parent integrates

A finished worker has produced a *proposal*. Between that and the parent
worktree sit five checks:

```text
WorkerResult
  → scope + budget validation      WorkerResult::validate_against
  → base drift                     propose_integration
  → conflict detection             detect_conflicts
  → evidence gate                  evaluate_proposal
  → PawGate / human approval       IntegrationApproved
  → apply                          IntegrationApplied
```

The last three are enforced **by the durable log**, not by daemon control flow.
`SessionState::validate_event` refuses `IntegrationApplied` unless the record is
`Approved`, refuses `IntegrationApproved` while a non-auto-mergeable conflict is
outstanding, and refuses an applied digest that differs from the approved one.
Since `SessionStore::append` runs the reducer before it persists, a buggy or
malicious caller cannot write the event either.

## 2. Where things live

| Concern | Crate / module |
| --- | --- |
| Typed contracts, authority fold, budgets | `runtime-core::delegation` |
| Delegation classifier (delegate or not) | `runtime-core::delegation::decision` |
| Conflict detection, integration decisions | `runtime-core::delegation::integration` |
| Durable events + projection | `runtime-core` (`SessionEvent`, `SessionState`) |
| Ceiling lattice (`meet`, `glob_covers`) | `runtime-core::tool` |
| Delegated judgment | `pawgate-runtime` (`Policy::evaluate_delegated`) |
| Worker worktrees, patches, cleanup | `delegation-runtime::workspace` |
| DAG scheduler, restart recovery | `delegation-runtime::scheduler` |
| Capability → specialist routing | `delegation-runtime::routing` |
| Worker context assembly | `delegation-runtime::context` |
| Patch application, hunk selection | `delegation-runtime::integrate` |
| Review results, bounded repair | `delegation-runtime::review` |
| Orchestration, HTTP, worker execution | `purrcode-daemon::delegation` + `lib.rs` |

The pure decisions live in `runtime-core` so they can be reasoned about and
replayed without a filesystem; the crates above it can only express decisions
those types already permit.

## 3. Worker isolation

Writer workers get their own git worktree. Reviewers get a read-only view of the
parent and **no worktree at all** — creating one because it is convenient would
hand a reviewer write authority nobody delegated.
`WorkerWorkspaceRecord::is_coherent` refuses both incoherent shapes, and the
reducer refuses the assignment event that carries one.

### Why worker worktrees are siblings, not children

The PRD draws worker worktrees nested under the parent's. Physically nesting
them would put worker files *inside* the parent's working tree, where git would
report them as untracked changes belonging to the parent — the parent's own diff
would silently contain every worker's work. They are therefore created as
siblings under `<repo>/.purrcode/worktrees/<worker-uuid>`, and the parent/child
relationship is carried in the record instead of in the path.

### Seed-and-commit

A worker is checked out at the parent's base commit, then the parent's
uncommitted work is applied **and committed** as the worker's base. Without the
commit, the worker's eventual diff would re-propose everything the parent had
already done, and the parent would be asked to integrate its own work back into
itself. With it, `git diff` in the worker's worktree is exactly that worker's
contribution.

## 4. Deciding whether to delegate

The classifier's most important answer is **no**.

```text
benefit  = parallelizable components + review value + spread across modules
cost     = fixed planning + per-worker setup, context, integration
delegate ⟺ benefit − cost ≥ 1
```

A localized fix short-circuits to `Single` before the arithmetic runs.
Delegation is not a user-facing mode: v1.3's "no Plan / Build toggle" rule
holds, and `POST /v1/sessions/{id}/delegations` may answer `single` with zero
workers no matter how many units the caller proposed. That answer is recorded as
a `DelegationPlanned` event, so "why did this run as one agent?" is answerable
later.

## 5. Conflicts

| Two workers touched… | Result |
| --- | --- |
| Different files | No conflict |
| The same file, disjoint hunks | `SameFileDifferentHunks` — deterministic merge may be attempted, then validated |
| The same base lines | `SameHunk` — **never** auto-merged |
| A file whose extent could not be parsed (binary) | `SameHunk`, conservatively |
| A base that has since moved | `BaseDrift` |
| A path outside the delegated scope | `ScopeViolation` — rejected outright |

Overlap is judged in *old-file* coordinates, because that is the frame both
patches share. A pure insertion (`@@ -N,0`) claims the single line it is anchored
to, so two workers inserting different code at the same point conflict instead of
one silently winning.

## 6. Recovery

The scheduler is a pure function of the durable projection, so there is no
scheduler state to lose. After a restart:

| Worker state at crash | After restart |
| --- | --- |
| Completed with a result | Left alone. `DelegationWorkerStarted` is refused by the reducer |
| Running | `Reconcile` — its worktree is retained, its patch preserved, it is not rerun |
| Awaiting a decision | Still awaiting; `IntegrationApplied` without approval is refused |
| Planned / Ready | Scheduled normally |

`retained_worker_worktrees()` answers "which directories hold an unresolved
patch?" from the projection, which is written in the same transaction as the
event precisely so the two can never disagree by one crash.

## 7. Resource governance

Worker budgets are *subdivisions* of the parent's remaining budget, never
independent ones — `clamp_to_remaining` is the only way a budget reaches an
admitted delegation. Parent usage includes child usage: every
`DelegationResultRecorded` folds the worker's usage into the session ledger.

Defaults: parallelism 3 (hard maximum 5), 6 workers per session, 600k worker
input tokens, delegation depth **1**. A specialist cannot delegate again — the
depth check is in `admit`, not in a policy file.

---

## 8. Repair

At most one automatic repair cycle, or two when the failure is a compile/test
error whose output names what broke. Then `NeedsAttention` and control returns
to the main agent. A repair is a **new** delegation with the same scope and
specialist, not a restart of the finished one: restarting would reopen a
terminal record, which is exactly what at-most-once forbids.

Attribution is by changed path. A failure in a file no worker touched is
reported as `unattributed` and handed back to the main agent rather than blamed
on whichever worker ran last.

## 9. Release gates

| Gate | Status | Evidence |
| --- | --- | --- |
| No worker can exceed parent authority | ✅ | `admitted_authority_is_within_every_input_over_a_generated_sweep`, `a_read_only_parent_cannot_delegate_write_authority`, `a_worker_writing_outside_its_delegated_paths_is_denied_by_pawgate` |
| Writer workers never share a writable worktree | ✅ | `two_writer_workers_edit_independently_in_their_own_worktrees`, `workspace_records_refuse_a_shared_writable_worktree`, `two_writers_cannot_be_assigned_the_same_worktree` |
| All worker changes enter through an IntegrationProposal | ✅ | `a_patch_cannot_be_applied_without_an_approval`, `accepting_an_unproposed_delegation_is_refused` |
| Same-hunk conflicts never auto-merge | ✅ | `the_same_hunk_is_never_auto_merged`, `two_workers_editing_the_same_hunk_produce_an_explicit_conflict`, `an_unresolved_conflict_cannot_be_approved` |
| Every WorkerResult has evidence provenance | ✅ | `a_finding_without_provenance_is_refused`, `review_pass_is_computed_not_claimed` |
| Completed workers survive restart without rerun | ✅ | `a_completed_worker_survives_restart_and_is_never_rerun` |
| Pending approvals survive restart | ✅ | `a_pending_approval_and_its_worktree_survive_restart` |
| Worker budgets are parent-bounded | ✅ | `child_budget_cannot_exceed_the_parents_remaining_budget`, `worker_budgets_are_clamped_to_what_the_session_has_left` |
| Delegation depth bounded to one level | ✅ | `delegation_depth_is_bounded_to_one_level` |
| Simple tasks stay single-agent | ✅ | `a_rename_stays_single_agent`, `a_simple_task_is_answered_single_agent_with_a_reason` |
| Single-agent regression suite green | ✅ | Full workspace test run |
| Linux / macOS / Windows CI green | ⏳ | macOS verified locally; CI matrix runs on push |
| Collaborative dogfood passes | ❌ | See §11 |

## 10. Non-goals (unchanged from the PRD)

Unbounded swarms, recursive delegation, debate/vote agents, workflow editors,
cloud workers, chat-platform agents, scheduled autonomous jobs, marketplace,
agent-generated agent definitions, workers merging their own patches, workers
sharing a writable worktree. None of these are present, and the depth bound and
the integration gate make the last two unreachable rather than merely absent.

## 11. What is not yet proven

Stated plainly, because a release document that overclaims is worse than one
that admits a gap.

**PR15 (dogfood & benchmark) has not been run.** The delegation path executes
end to end — plan, route, provision, run a model-driven worker, propose,
conflict-check, approve, apply — and every stage is covered by tests including
ten against real git. But the comparative benchmark the PRD asks for (10–20 real
engineering tasks, single-agent vs collaborative, measuring success rate,
regression count, token cost and coordination overhead) requires many live model
runs and has not been performed. Until it has, the claim "delegation improves
outcomes enough to justify its cost" is a design argument supported by the
classifier's cost model, not a measured result.

**Worker execution is a bounded read/write loop, not the full agent.** A
delegated specialist proposes one action per turn (read, write, delete), judged
by `Policy::evaluate_delegated` and executed through the ordinary sandbox. It
does not have registry tools, MCP, or skills — those are primary-agent surfaces
in v1.3 and extending them to workers is a deliberate follow-up, not an
oversight. A worker that tries reports a refusal it can act on.

**The main agent does not yet delegate on its own initiative.** Planning is a
daemon command (`POST /v1/sessions/{id}/delegations`); the classifier decides
whether to delegate, but the trigger comes from the client rather than from the
main agent's own turn loop. Wiring the planner into `run_until_pause` is the
remaining piece of the north-star flow in PRD §2.

**Selected-hunk integration is text-only.** A binary patch must be accepted or
rejected whole; `select_hunks` refuses it explicitly rather than producing a
patch that would silently drop the binary.
