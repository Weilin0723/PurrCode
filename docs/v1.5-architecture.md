# PurrCode v1.5 — Alignment-First Autonomous Development

> v1.4: workers propose, evidence proves, the parent integrates.
> v1.5: the user defines the outcome, and PurrCode keeps itself aligned until
> the evidence says the outcome is actually met.

v1.4 settled how changes are made safely. It said nothing about whether the
change was the one the user wanted — and a coding agent fails that way far more
often than it fails to compile. Build passes, tests pass, lint passes, and the
settings page is still unusable.

## The loop

```text
user message
     ↓  intent compiler
expectation contract  ─────────────────┐  re-injected into every prompt
     ↓                                 │
implementation                         │
     ↓                                 │
deterministic validation               │
     ↓                                 │
requirement coverage review ───────────┤  none of the three sees the
independent code review ───────────────┤  implementer's transcript
user alignment review ─────────────────┘
     ↓
delivery gate  (reads the log, not the model)
     ├── ready ─────────────────────→ session completes
     ├── blocking findings ─────────→ bounded correction → re-review
     ├── requirements outstanding ──→ keep working, with the gate's reason
     └── needs a decision ──────────→ the user, with what was tried
```

| | Where it lives |
| --- | --- |
| Expectation contract, statuses, revision | `runtime-core/src/expectation/` |
| Findings, review records, fresh-context containment | `runtime-core/src/review.rs` |
| Delivery gate | `runtime-core/src/expectation/delivery.rs` |
| Bounded correction ledger | `runtime-core/src/correction.rs` |
| Intent compiler, reviewers, repair driver | `alignment-runtime/` |
| The loop, on a real session | `agent-runtime/src/alignment.rs` |
| Presentation contracts | `ui-contracts/src/alignment.rs` |
| Projection and the one route that serves it | `purrcode-daemon/src/alignment_presentation.rs` |
| The panel | `purrcode-ide/src/app/alignment.rs` |
| Benchmark schema, catalog, scoring | `evaluation-runtime/src/alignment.rs` |
| Benchmark runner and fixture | `evaluation-runtime/src/bin/`, `benchmarks/alignment-fixture/` |

### Why the durable half lives in `runtime-core`

The v1.5 plan proposed `crates/expectation-runtime`, `crates/review-runtime`
and `crates/correction-runtime`. The durable, replayable *types* went into
`runtime-core` instead, following the split `delegation.rs` and
`delegation-runtime` already use: pure state and its reducer on one side,
I/O-touching behaviour on the other.

The reason is not tidiness. A contract that is not in the session log cannot
survive a daemon restart, and an agent that resumes without its requirements
resumes without knowing what it is for. `alignment-runtime` is the model-facing
half — the intent compiler, the reviewer harnesses, the repair driver — which is
behaviour, not state.

## The rules, and where they are enforced

Each of these is enforced in code that runs, not asked for in a prompt. The
component being constrained is in every case the one writing the prose.

**A requirement must quote the user.** The intent compiler refuses a clause
whose quotation does not appear in a message the user actually sent, and the
runtime decides which message it came from rather than believing the model's
index. Intent does not drift in one step — *don't clutter the UI* → *simplify
the UI* → *reduce the options* → *remove the advanced settings* — and every step
looks reasonable next to the one before it. One bounded retry naming the
offending clause, because a paraphrase is recoverable when you say what was
wrong with it and permanent when you don't.

**Nothing is verified without evidence, and evidence must resolve.** Refusing an
empty evidence list closes the crude version. `EvidenceId::new()` clears it and
establishes nothing, which is what a reviewer under pressure to close a
requirement reaches for without meaning to deceive anyone. So evidence is a
durable record before it is a citation, and a citation must resolve to a record
made *against the same requirement* — the likelier mistake being the settings
test cited for the MCP requirement, since the ids are opaque and nothing about a
UUID says what it belongs to. A contract also cannot arrive already verified.

**Counts, not percentages.** `RequirementTally` is five integers and prints
`6 / 7 requirements verified`. There is deliberately no percentage accessor, and
none in the UI contracts or the panel either. `94% aligned` cannot be wrong, so
it cannot be informative — and it is precisely the number an agent would reach
for to make an unfinished task look nearly done.

**A correction revises the contract; it does not append to it.** When the user
says *"no, I didn't mean delete the sidebar, it's just cramped"*, restating the
clause resets it to `Unverified` and names it in `invalidated`, so the deletion
stops counting as progress and only the affected work is re-planned.
`ExpectationContractRevised` stores the *correction* rather than the contract it
produced, and replay re-applies it — so a buggy writer cannot persist a state the
rules forbid and have recovery faithfully restore it.

**Reviewers judge; repair agents repair.** A reviewer that fixes what it finds
has destroyed its own evidence: the finding and the fix become one unverifiable
act. The reviewers here return findings and verdicts and have no field for an
edit. `ReviewKind::{IndependentCode, UserAlignment}` must run with
`ReviewContext::Fresh`, and that is now true by construction —
`FreshReviewInput` has no `messages` field, no `history` field and no
`Vec<ModelMessage>` constructor, so there is nowhere for the implementer's
transcript to arrive. The failure is otherwise silent: a contaminated reviewer
still produces confident findings, it just mostly agrees.

**Completion is a state transition.** An agent asked whether it is finished will
usually say yes; it is the natural continuation of a transcript full of work. So
it is not asked. `DeliveryGateEvaluated` carries no verdict — the reducer
computes one from the contract, the outstanding findings, what the diff actually
touched, the bounds the contract set and the unresolved worker integrations, and
stores its own computation. `DeliveryAssessment`'s fields are private,
`evaluate` is its only constructor, and deserialisation re-derives the state from
the blockers rather than trusting the one on the wire.

The one input the log cannot decide is which checks a task required — a project
with no test suite is not a project with a failing one — so that list is
declared, and cross-checked: a declared pass the log does not support is
refused, and a check the log shows failing cannot be left off.

`SessionCompleted` re-runs the gate rather than reading the stored verdict. A
stored verdict is a fact about the moment it was computed, and *gate clears →
reviewer speaks → agent completes* is exactly the sequence a stale read lets
through.

## Bounded correction

Two automatic cycles for findings involving judgement; three when every
outstanding blocker is deterministic. A failing test is a fact with an
unambiguous target and attempts converge; a reviewer's reading of "this still
feels cluttered" is a judgement, and a third attempt at satisfying one mostly
produces a differently-shaped disagreement. One judgement-shaped finding pulls
the whole round to the tighter budget, because the loop cannot converge faster
than its slowest member. When the budget is gone the task goes to the user with
what was tried — it does not silently pass and does not silently fail.

Whether a repair worked is decided by re-review, matched on whether the same
complaint came back against the same requirement. That is a heuristic, and its
failure mode is worth stating: a second, different problem in the same place
reads as the first one surviving. It errs toward *not* closing findings.

## What the user sees

The panels are one thing in the UI, so they are one type (`AlignmentView`) and
one route. Five independent fetches can disagree with each other — a contract
read before a correction beside findings read after it describes a session that
never existed.

Changes are grouped by the requirement they serve, attributed from what the
reviewers and the evidence actually named rather than from the agent's account
of what it was doing. A file nothing points at lands in a group that says so,
and that group is the point: in a flat list, work nobody asked for looks exactly
like work that was.

A requirement shown as verified whose trace is empty is marked unsupported on
the row itself. A tick next to an empty evidence list is the false `Done` in
presentation form, and a user should not have to expand every row to find it.

A session with no contract is reported as exactly that rather than as an empty
panel: the two mean opposite things, and an empty panel reads as nothing to
worry about.

## Degrading honestly

If the intent compiler cannot produce a contract whose clauses quote the user,
the session says so in the conversation and continues on the v1.4 path. That is
an honest degradation and not a quiet one — the benchmark counts a completion
with no gate as a false `Done`, so this route cannot become the comfortable way
to finish.

## The benchmark

`evaluation-runtime/src/alignment.rs` — 20 tasks: 5 simple, 10 complex, 5
alignment traps. `benchmarks/alignment-fixture/` is the repository they are
scored against: a small application with real seams in it — duplicated HTTP
setup, an off-by-one, two modules that disagree about an id, a settings panel
where everything is visible at once. A fixture with nothing wrong with it gives
every task the same answer and measures nothing.

The design lesson comes from v1.4's own release bar, which **could be cleared by
a build that never delegated at all**: every decline scored as favourable, so
three of four conditions passed and the fourth could not fail. A bar that can
only fail in one direction measures enthusiasm, not correctness.

So every gate here is paired. A runtime that reviews nothing fails
(`correction_success` requires the reviewers to have actually found something
across twenty tasks); a runtime that reviews forever fails too (`over_reviewed`
holds simple tasks to 30% review overhead and complex ones to 60%). One that
never claims completion fails; one that claims it falsely fails harder.

The central metric is `falsely_reported_done` — the agent presented the work as
finished when the gate had not granted it, or when no gate ran at all. If the
delivery gate holds this is structurally impossible; the benchmark exists to
find out whether it holds in practice rather than only in the reducer's tests.

Scoring comes from two places, and neither is the agent. The **durable log**
answers whether the gate ran and what it concluded. The **tree the run left
behind** answers whether the requirements were met — it cannot come from the
session's own reviewers, because they are the thing under test and a run where
they were wrong looks identical from inside to one where they were right. Every
`TaskCheck` names a path the fixture actually has, and a unit test enforces
that: v1.4's catalog scored against `src/retry.rs`, `web/` and `migrations/` in
a `crates/`-based workspace, and nobody noticed until somebody tried to run it.

```bash
cargo run -p purrcode-evaluation-runtime --features benchmark \
  --bin purrcode-alignment-benchmark -- \
  --daemon http://127.0.0.1:4477 --token "$PURRCODE_TOKEN" \
  --repository benchmarks/alignment-fixture --out target/alignment-report.md
```

It exits non-zero when the bar is not met, so CI does not need a human to read
the markdown.

## Status

Implemented, with tests:

- Expectation contract, statuses, revision, sticky-alignment brief
- Durable evidence, and citations that must resolve to it
- Finding contract, review records, fresh-context containment by construction
- Delivery gate, its four outcomes, and a `Ready` no caller can write
- Bounded correction ledger and lifecycle phases
- Intent compiler, three reviewers, repair driver
- The loop wired into `NativeAgent` and attached by the daemon
- Durable events and reducer invariants for all of the above
- `Reviewer` / `AlignmentReviewer` / `RepairWorker` model roles, billed to the
  session log so review overhead is a measured fact
- v1.5 presentation contracts, the daemon projection, and the IDE panel
- 20-task alignment benchmark: schema, catalog, mechanical checks, live runner,
  and the fixture repository it scores against

**Not yet done.** The benchmark has not been run against a live provider, so
this branch carries a runnable exam and no result. That is the remaining gap
between "v1.5 is built" and "v1.5 is measured", and it needs provider
credentials and a few hours of wall-clock rather than more code.

The v1.4 collaborative benchmark still scores against paths no repository in
this workspace has. It can now be pointed at `benchmarks/alignment-fixture`,
whose layout its catalog was written against, but its own checks have not been
brought up to the mechanical standard the alignment catalog now holds.
