# PurrCode v1.5 — Alignment-First Autonomous Development

> v1.4: workers propose, evidence proves, the parent integrates.
> v1.5: the user defines the outcome, and PurrCode keeps itself aligned until
> the evidence says the outcome is actually met.

v1.4 settled how changes are made safely. It said nothing about whether the
change was the one the user wanted — and a coding agent fails that way far more
often than it fails to compile. Build passes, tests pass, lint passes, and the
settings page is still unusable.

## The three P0s

| | What it guarantees | Where it lives |
| --- | --- | --- |
| Expectation Contract | Intent outlives the conversation | `runtime-core/src/expectation/` |
| Independent review | The reviewer is not the implementer | `runtime-core/src/review.rs` |
| Delivery gate | Completion is a state transition, not a claim | `runtime-core/src/expectation/delivery.rs` |

### Why these live in `runtime-core`

The v1.5 plan proposed `crates/expectation-runtime`, `crates/review-runtime`
and `crates/correction-runtime`. The durable, replayable *types* went into
`runtime-core` instead, following the split `delegation.rs` and
`delegation-runtime` already use: pure state and its reducer on one side,
I/O-touching behaviour on the other.

The reason is not tidiness. A contract that is not in the session log cannot
survive a daemon restart, and an agent that resumes without its requirements
resumes without knowing what it is for. The separate crates remain the right
home for the model-facing halves — the intent compiler, the reviewer harnesses,
the repair driver — which are behaviour, not state.

## The rules, and where they are enforced

Each of these is enforced in code that runs, not asked for in a prompt. The
component being constrained is in every case the one writing the prose.

**Nothing is verified without evidence.** `RequirementStatus::Verified` with an
empty evidence list is refused by `ExpectationContract::validate` *and* again by
the session reducer, so an unevidenced pass cannot enter the log even if a
reviewer tries to write one. `Unknown` is a distinct state from `Unverified` and
does not clear delivery: an agent that ships on "I could not tell" is the false
`Done` this release exists to stop. A waiver must carry a reason.

**Counts, not percentages.** `RequirementTally` is five integers and prints
`6 / 7 requirements verified`. There is deliberately no percentage accessor, and
none in the UI contracts either. `94% aligned` cannot be wrong, so it cannot be
informative — and it is precisely the number an agent would reach for to make an
unfinished task look nearly done.

**A correction revises the contract; it does not append to it.** When the user
says *"no, I didn't mean delete the sidebar, it's just cramped"*, restating the
clause resets it to `Unverified` and names it in `invalidated`, so the deletion
stops counting as progress and only the affected work is re-planned.
`ExpectationContractRevised` stores the *correction* rather than the contract it
produced, and replay re-applies it — so a buggy writer cannot persist a state the
rules forbid and have recovery faithfully restore it.

**Reviewers judge; repair agents repair.** A reviewer that fixes what it finds
has destroyed its own evidence: the finding and the fix become one unverifiable
act. `ReviewKind::{IndependentCode, UserAlignment}` must run with
`ReviewContext::Fresh`, and the reducer refuses a review that was handed the
implementer's transcript. The failure is otherwise silent — a contaminated
reviewer still produces confident findings, it just mostly agrees.

**Completion is a state transition.** An agent asked whether it is finished will
usually say yes; it is the natural continuation of a transcript full of work. So
it is not asked. `delivery::evaluate` reads the contract, findings, validations
and diff. The reducer refuses a `DeliveryGateEvaluated` whose state is `Ready`
while blockers remain, however that assessment was produced.

## Bounded correction

Two automatic cycles for findings involving judgement; three when every
outstanding blocker is deterministic. A failing test is a fact with an
unambiguous target and attempts converge; a reviewer's reading of "this still
feels cluttered" is a judgement, and a third attempt at satisfying one mostly
produces a differently-shaped disagreement. One judgement-shaped finding pulls
the whole round to the tighter budget, because the loop cannot converge faster
than its slowest member. When the budget is gone the task goes to the user with
what was tried — it does not silently pass and does not silently fail.

## The benchmark

`evaluation-runtime/src/alignment.rs` — 20 tasks: 5 simple, 10 complex, 5
alignment traps.

The design lesson comes from v1.4's own release bar, which **could be cleared by
a build that never delegated at all**: every decline scored as favourable, so
three of four conditions passed and the fourth could not fail. A bar that can
only fail in one direction measures enthusiasm, not correctness.

So every gate here is paired. A runtime that reviews nothing fails
(`correction_success` requires the reviewers to have actually found something
across twenty tasks); a runtime that reviews forever fails too (`over_reviewed`
holds simple tasks to 30% review overhead and complex ones to 60%). One that
never claims completion fails; one that claims it falsely fails harder.

The central metric is `falsely_reported_done` — the agent presented the work as
finished when the gate had not granted it, or when no gate ran at all. If the
delivery gate holds this is structurally impossible; the benchmark exists to
find out whether it holds in practice rather than only in the reducer's tests.

## Status

Implemented, with tests, on `feature/v1.5-alignment-first-autonomous-development`:

- Expectation contract, statuses, revision, sticky-alignment brief
- Finding contract, review records, fresh-context containment
- Delivery gate and its four outcomes
- Bounded correction ledger and lifecycle phases
- Durable events and reducer invariants for all of the above
- 20-task alignment benchmark schema, catalog and scoring
- v1.5 presentation contracts (`ui-contracts/src/alignment.rs`)
- `Reviewer` / `AlignmentReviewer` / `RepairWorker` model roles

**Not yet built.** These are behaviour rather than state, and each needs a live
provider to be worth anything:

- The intent compiler — turning a user message into a contract via the model
- The reviewer harnesses that produce findings from a real diff
- The repair driver that consumes findings and re-reviews
- IDE rendering of the v1.5 panels (the contracts exist; nothing draws them yet)
- A live benchmark runner, and the fixture repository it needs

The last point carries over from v1.4 and is worth stating plainly: the v1.4
collaborative benchmark cannot currently produce a meaningful result, because
its catalog scores against paths (`src/retry.rs`, `web/`, `migrations/`) that do
not exist in a `crates/`-based workspace. A fixture repository has to be built
before either benchmark can be run for real.
